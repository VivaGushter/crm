# Master CRM

Внутренняя CRM для работы с заявками мастера: календарь выездов, карточки клиентов, статусы работ, назначение исполнителей и базовая аналитика.

Проект развёрнут на VPS и используется как рабочее приложение. Главный принцип дальнейшей разработки — **не ломать привычный интерфейс и рабочий процесс**: изменения сначала проверяются в отдельной среде и вносятся небольшими, обратимыми шагами.

## Текущий статус

На текущем этапе CRM работает в production.

- Приложение запускается через `systemd`-службу `master-crm.service`.
- Production-процесс слушает `127.0.0.1:8000`; внешний доступ при необходимости обеспечивается веб-сервером/прокси.
- Backend построен на FastAPI и разделён на модули в `backend/`.
- Основная база — SQLite: `data/crm.db`.
- Интерфейс в `frontend/index.html` сохранён на базе прежнего рабочего дизайна: дашборд, крупные показатели, календарь месяц/неделя/день, карточки заявок и управление пользователями.
- Новые и существующие заявки создаются, читаются, редактируются и удаляются через API.
- Пользователи и роли хранятся в SQLite; доступны роли `admin` и `user`.
- Авторизация API использует HTTP Basic Auth.

## Возможности

### Работа с заявками

- Создание, изменение и удаление заявок.
- Клиент, дата и время выезда, адрес, телефон, цена, комментарий.
- Назначение ответственного исполнителя.
- Статусы:
  - `new` — новая;
  - `scheduled` — назначена;
  - `work` — в работе;
  - `done` — завершена;
  - `cancel` — отменена.
- Поиск по клиенту, адресу, телефону и комментарию.
- Фильтрация по статусу, исполнителю и дате.
- Календарное представление заявок за месяц, неделю и выбранный день.

### Дашборд

На главной странице отображаются:

- всего заявок;
- заявок на сегодня;
- назначенных заявок;
- завершённых заявок;
- сумма завершённых заявок.

### Пользователи

Администратор может:

- просматривать список пользователей;
- добавлять пользователей;
- менять имя, роль и пароль;
- удалять пользователей, кроме своей текущей учётной записи.

### Источник и связь

Backend уже поддерживает дополнительные поля заявки:

| Поле | API-значения | Назначение |
|---|---|---|
| `source` | `unknown`, `avito`, `house_chats` | Источник обращения |
| `contact_method` | `""`, `avito`, `phone`, `telegram`, `max` | Способ связи с клиентом |

Для новой заявки backend требует заполненный источник: `unknown` при создании не допускается.

**Текущее временное поведение UI:** старая форма пока не показывает эти поля. Чтобы не нарушать создание заявок, frontend отправляет скрытые значения:

```json
{
  "source": "avito",
  "contact_method": ""
}
```

Это совместимый переходный механизм. Следующий UI-этап — добавить пользователю видимые поля выбора источника и способа связи, сохранив существующий дизайн.

## Структура проекта

```text
/opt/master-crm/
├── app.py                    # Точка входа FastAPI, маршруты, выдача frontend
├── backend/
│   ├── auth.py               # Basic Auth, хеширование паролей, проверка ролей
│   ├── config.py             # Пути, статусы, источники, способы связи
│   ├── db.py                 # SQLite-подключение, инициализация и миграции
│   ├── schemas.py            # Pydantic-схемы запросов
│   └── routes/
│       ├── requests.py       # API заявок
│       ├── reports.py        # API отчёта по периоду
│       └── users.py          # API пользователей
├── frontend/
│   └── index.html            # Текущий рабочий интерфейс CRM
├── static/                   # Экспериментальные/будущие вынесенные статические файлы
├── data/
│   └── crm.db                # Production SQLite-база — не хранить в Git
├── backups/                  # Локальные резервные копии — не хранить в Git
├── requirements.txt
├── master-crm.service        # systemd unit
└── nginx-master-crm.conf     # Пример nginx-конфигурации
```

> Пути выше описывают production-развёртывание. В Git должны храниться исходный код, безопасные конфигурационные шаблоны и документация, но не реальные базы данных, бэкапы, пароли и токены.

## Быстрый запуск

### Подготовка окружения

```bash
cd /opt/master-crm
source venv/bin/activate
```

### Проверка импортов и схемы БД

```bash
/opt/master-crm/venv/bin/python -c \
  "from app import app; from backend.db import init_db; init_db(); print('Импорт и миграция: OK')"
```

### Локальный запуск для диагностики

```bash
cd /opt/master-crm
/opt/master-crm/venv/bin/uvicorn app:app --host 127.0.0.1 --port 8001
```

Для временной проверки из браузера на другом устройстве:

```bash
/opt/master-crm/venv/bin/uvicorn app:app --host 0.0.0.0 --port 8001
```

Не оставляйте тестовый сервер на `0.0.0.0:8001` доступным постоянно. Это только диагностический режим; production обслуживается через systemd на порту `8000`.

## Production

### Управление службой

```bash
systemctl status master-crm.service --no-pager
systemctl restart master-crm.service
journalctl -u master-crm.service -n 100 --no-pager
```

### Проверка ответа приложения

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/
```

Ожидаемый результат: `200`.

### Проверка защищённого API

```bash
curl -i http://127.0.0.1:8000/api/requests
```

Без авторизации ожидается `401 Unauthorized`.

Проверка с учётными данными:

```bash
curl -i \
  -u 'ЛОГИН:ПАРОЛЬ' \
  http://127.0.0.1:8000/api/users
```

Не передавайте реальные логины и пароли в публичные чаты, историю команд, скриншоты или Git.

## Авторизация и роли

API защищён HTTP Basic Auth.

- Логин — поле `users.id`.
- Отображаемое имя — `users.name`.
- Роль — `users.role`: `admin` или `user`.
- Пароль в БД хранится как SHA-256-хеш в `users.password_hash`.
- Сравнение хеша выполняется через `secrets.compare_digest`.

Заголовок, который frontend отправляет к API:

```http
Authorization: Basic BASE64(логин:пароль)
```

### Замечание по безопасности

Текущий legacy-интерфейс может сохранять учётные данные при включении «Запомнить меня». В рамках ближайшей технической работы это нужно заменить на более безопасную схему: сессионное хранение или серверные сессии/токены с ограниченным сроком жизни. Это изменение должно быть протестировано отдельно, чтобы не сломать привычный вход.

## API

Все перечисленные API требуют HTTP Basic Auth.

### Заявки

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/requests` | Список заявок с фильтрацией |
| `POST` | `/api/requests` | Создание заявки |
| `PUT` | `/api/requests/{request_id}` | Изменение заявки |
| `DELETE` | `/api/requests/{request_id}` | Удаление заявки |

Параметры `GET /api/requests`:

```text
search
status
assignee
source
contact_method
date_from
date_to
```

### Пользователи

| Метод | Путь | Доступ |
|---|---|---|
| `GET` | `/api/users` | Авторизованный пользователь |
| `POST` | `/api/users` | Только admin |
| `PUT` | `/api/users/{user_id}` | Только admin |
| `DELETE` | `/api/users/{user_id}` | Только admin |

### Отчёт

```text
GET /api/report?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD
```

Ответ содержит:

- `total` — всего заявок за период;
- `active` — новые, назначенные и находящиеся в работе;
- `completed` — завершённые;
- `cancelled` — отменённые;
- `revenue` — сумма завершённых заявок;
- `by_source` — разбивка по источникам.

## Изменения и выкладка

### Правило работы

Не редактируйте production «наживую» без резервной копии и понятного отката.

Минимальный безопасный цикл:

1. Создать локальный backup.
2. Внести одно логически цельное изменение.
3. Проверить синтаксис и API на тестовом запуске.
4. Проверить интерфейс в браузере.
5. Перезапустить `master-crm.service`.
6. Проверить статус службы, HTTP `200` и последние логи.
7. При проблеме откатить только изменённые файлы; базу восстанавливать лишь при необходимости.

### Создание backup

```bash
cd /opt/master-crm
mkdir -p backups
STAMP=$(date +%F-%H%M%S)

cp -a app.py "backups/app.py.${STAMP}"
cp -a frontend/index.html "backups/index.html.${STAMP}"
cp -a data/crm.db "backups/crm.db.${STAMP}"
```

### Проверки перед перезапуском

```bash
cd /opt/master-crm

/opt/master-crm/venv/bin/python -m py_compile \
  app.py backend/*.py backend/routes/*.py

systemctl restart master-crm.service
systemctl status master-crm.service --no-pager
journalctl -u master-crm.service -n 50 --no-pager

curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/
```

## План развития

Развитие должно идти поэтапно. Приоритет — устойчивость рабочей CRM, сохранение привычного интерфейса и защита данных.

### Приоритет 1: гигиена репозитория и безопасность

- Удалить из Git исторические SQLite-базы, архивы, локальные backup-файлы и дубли `app.py`.
- Усилить `.gitignore`, чтобы исключить `data/*.db*`, `backups/`, архивы и локальные секреты.
- Проверить историю и рабочую ветку на случайно закоммиченные пароли, токены и клиентские данные.
- Не хранить production-дампы и реальные персональные данные в GitHub.
- Подготовить безопасный шаблон конфигурации, если появятся переменные окружения.

### Приоритет 2: отдельная staging-среда

Сейчас тестовый запуск на `8001` использует ту же базу, что и production. Это риск: тестовая запись или миграция затрагивает реальные данные.

Нужно создать отдельную staging-среду:

- отдельная директория либо отдельное virtualenv-конфигурирование;
- отдельная тестовая SQLite-база;
- отдельный systemd unit или явная команда запуска;
- отдельный порт;
- безопасное копирование структуры без публикации production-данных.

### Приоритет 3: завершить источник и связь в UI

Backend уже готов. Следующая продуктовая задача — аккуратно расширить существующую форму без редизайна:

- добавить видимый обязательный select «Источник»;
- варианты: «Авито» и «Домовые чаты»;
- добавить select «Способ связи»;
- варианты: «Не указано», «Авито», «Звонок», «Telegram», «Max»;
- показать оба значения в карточках заявок;
- добавить фильтры по источнику и способу связи;
- сохранить действующий дашборд, календарь и карточный стиль.

### Приоритет 4: отчёт в текущем дизайне

Добавить кнопку **«Отчёт»** в верхнюю панель существующего интерфейса. По нажатию должно открываться модальное окно:

- период «с» / «по»;
- всего заявок;
- активные;
- завершённые;
- отменённые;
- выручка по завершённым;
- таблица по источникам: «Авито», «Домовые чаты», «Не указан»;
- для каждого источника: всего, завершено, выручка.

Использовать существующий endpoint `/api/report`; не заменять главную страницу отдельной упрощённой таблицей.

### Приоритет 5: качество и эксплуатация

- Добавить минимальные автоматические проверки API и миграций.
- Документировать точный процесс deploy и rollback.
- Настроить ротацию/контроль журналов systemd.
- Проверить права доступа к файлам базы и backup-копиям.
- После стабилизации рассмотреть экспорт заявок/отчётов, уведомления и интеграции.

## Работа с Git

В репозитории должны храниться только исходный код, документация и безопасные шаблоны конфигурации.

Не коммитить:

```text
data/*.db
data/*.db-*
backups/
*.tar.gz
*.zip
*.bak
*.backup
.env
__pycache__/
*.pyc
venv/
```

Перед любым коммитом рекомендуется проверить состояние:

```bash
git status --short
git diff --check
git diff --cached --check
```

Для изменений кода предпочтительный процесс:

```bash
git checkout -b feature/short-description
# Внести и протестировать одно изменение
git add <нужные_файлы>
git commit -m "Краткое описание изменения"
git push -u origin feature/short-description
```

Затем создать Pull Request в `main`. Прямые изменения в `main` допустимы только для срочного и полностью проверенного hotfix, с локальным backup до выкладки.

## Важные ограничения

- SQLite подходит для текущего небольшого объёма и двух пользователей, но требует резервных копий и аккуратности при конкурентных изменениях.
- HTTP Basic Auth передаёт пароль в каждом API-запросе; использовать только поверх HTTPS при внешнем доступе.
- SHA-256 без адаптивного password-hashing алгоритма не является оптимальной схемой для долгосрочной защиты паролей. Переход на Argon2id или bcrypt нужно выполнять отдельной миграцией с поддержкой старых хешей на период перехода.
- Не тестируйте создание/удаление заявок на production-базе, если запись не должна попасть в рабочие данные.
